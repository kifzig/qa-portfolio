Testing Process

The same workflow I run at Zelifcam on every feature and release, start to finish. Each step links to the skill it draws on.

1

Review Requirements

Before writing a single test case, I read the ticket and talk to the developer or PM about anything that isn't fully specified — expected behavior for edge cases, what's explicitly out of scope. Ambiguity gets resolved before testing starts, not argued about after a "bug" is filed that turns out to be intended behavior.

ClickUpRequirements review
Related skill: Requirements & Acceptance Criteria Review →
2

Identify Risks

Testing time is never unlimited, so I decide what actually needs coverage: high-traffic paths, areas that have broken before, anything touching auth or data integrity. For inputs, I use boundary value analysis and equivalence partitioning to pick the values worth testing instead of testing every possible value.

Risk-based testingBoundary value analysisEquivalence partitioning
Related skill: Test Design Techniques →
3

Write Test Scenarios

The requirement plus the identified risks become a set of test cases — main path, edge cases, negative cases — organized into a checklist so they're repeatable on the next release, not written from scratch every time.

Test casesTest plansChecklists
Related skill: Test Case & Test Plan Design →
4

Execute Tests

I run the test cases manually — functional testing on the new work, exploratory testing where the spec doesn't cover everything — and lean on Cypress for regression paths that are already stable and automated. Anything user-facing gets checked across browsers and through a full login/logout cycle.

Manual testingCypressCross-browser testing
Related skill: Manual & Exploratory Testing →
5

Log Defects

Every defect gets a reproducible report: exact steps, expected vs. actual result, a screen recording, and severity and priority set independently of each other. It's filed in ClickUp and tagged to the right developer with everything they need to start immediately.

Bug reportsSeverity vs. priorityClickUp
Related skill: Bug Reporting & the Defect Lifecycle →
6

Verify Fixes

Once a developer marks a defect fixed, I re-run the original repro steps against the fix build myself — not just confirming the code changed, confirming the reported behavior is actually gone before the ticket closes.

Regression verificationDefect tracking
Related skill: Bug Reporting & the Defect Lifecycle →
7

Perform Regression Testing

Before a release, I run a smoke pass first to confirm the build is stable, then a full regression pass covering prior defects — including anything just verified in step 6 — and core user workflows. The highest-traffic paths are also checked automatically by the Cypress suite.

Regression testingSmoke testingSanity testing
Related skill: Functional, Regression & Smoke/Sanity Testing →
8

Support Release

A final smoke test on the actual release candidate before sign-off, then monitoring after release with Rollbar for anything that slipped through. Any post-release hotfix goes through the same verify-and-regress steps before it's considered done.
